# Agent Release Remediation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The user forbids separate worktrees for this follow-on; work in the existing checkout. This authoring pass makes no implementation edits, test runs, or commits.

**Goal:** Make Agent release publication, first legacy upgrade, and failed-update supersession safe under durable source proof, one exact ZIP contract, and an uninterrupted maintenance hold.

**Architecture:** A shared .NET verifier supplies the Controller and a deployment-pinned local maintenance helper. A protocol-2 Agent uses a no-ack challenge exchange, while Controller SQLite transactions own proof, source binding, chain/head/generation and audit. The elevated helper maintains local lock, fence, immutable backup and fsynced journal across update/recovery; the web UI only issues explicit per-machine commands.

**Tech Stack:** .NET 10/C#, SQLite, ASP.NET Core TestServer, Windows PowerShell 5.1/PowerShell 7, Next.js/React/TypeScript, xUnit/Vitest.

**Spec:** `docs/superpowers/specs/2026-11-09-agent-release-remediation.md` (read it before implementation; it is the binding, self-contained requirements source).

## Global Constraints

- No separate worktree and no Reboot Restore Rx inspection or operation. No automatic machine reboot, service/firewall mutation or production rollout during implementation tests.
- New publishable/eligible release keeps `packageFormatVersion=1` and the six exact manifest keys, but `agentUpdateChallengeProtocol=2` in manifest and `Agent.dll` metadata; protocol-1 artifacts remain history and are ineligible for new update/supersession. A release-update feature gate defaults closed until every task and qualification gate passes; intermediate code must not enable live updates.
- ZIP compressed bytes 1..104857600; expanded regular bytes <=524288000; physical entries <=5000; materialized non-root nodes <=5000; normalized path <=240, segment <=100, depth <=16; manifest 1..65536/depth<=8; deps 1..16777216/depth<=32. Apply the complete normative contract in the spec, including CRC and ZIP structural consistency.
- User-facing update/recovery is explicit per machine. Started/inherited maintenance holds survive expiry, failure, restart and recovery. Approval and held allocation gates remain independent.
- The ZIP is inert data in elevated maintenance. Every executed updater/helper/script is independently pinned to deployed bytes. Native OS architecture controls helper selection and canonical paths, regardless of PowerShell bitness.
- Local maintenance fence continuously overrides Agent/Guard stream authority, and current plus pending lease state must be reconciled; unknown means held.
- Restore defaults to global rental/update quarantine until external epoch/history and each machine's local journal are reconciled. Existing rental readiness work is separate.
- Read the relevant `node_modules/next/dist/docs/` guide before any Next.js route/component edit, as required by `AGENTS.md`.

## Review Focus

1. Already deployed echo-only Agent receives a challenge-only response: it must never receive challenge-only 200 or clear pending results/active lease; Task 2 tests local behavior and Task 4 tests old-client/Controller compatibility.
2. CRC-only/data-descriptor tampered ZIP passes ordinary `ZipArchive` reads: publish/helper must reject with the same category; Task 1 corpus tests it.
3. Old updater with no new journal and no shared lock: import may proceed only after qualified exclusion/full restart; Task 7 tests old paths, boot IDs and ambiguity.
4. Delayed `ApplyLease` reopens stream after snapshot: maintenance fence wins continuously, even across pending initial/confirmation; Task 6 race tests it.
5. Restored snapshot predates an entire chain or allocation: global quarantine remains until independent complete history reconciles that machine; Task 9 tests both snapshot ages.

## File and interface map

`services/AgentPackage/` is the new pure bounded ZIP/metadata/inventory library. `services/AgentMaintenance/` is the self-contained, architecture-specific, trusted CLI with identity evidence, journal, lock and service adapter. Controller `Data/AgentUpdateState.cs` owns chain CAS/tickets/reports; new focused `Data/AgentUpdateProofState.cs` owns sync/source challenges and evidence, while `Data/SyncState.cs` consumes verified envelopes. `ControllerDatabaseMaintenance.cs` owns backup/restore quarantine. Existing PowerShell files become pinned bootstrap/host wrappers and use the CLI for archive/extracted validation and mutation. `src/app/api/admin/machines/[machineId]/agent-update-command/route.ts` and `AgentUpdateControl` expose explicit commands/status; they never infer safety from a fresh-looking heartbeat. The Agent sync client uses ordinary platform HTTPS certificate and hostname validation; only the existing PowerShell updater uses a configured trust-root thumbprint. Any new Agent certificate pinning would need a separately designed safe bootstrap/rotation protocol.

Keep migrations ordered after `013-agent-update-downloads.sql`: `014-agent-maintenance-chains.sql` for chain, operation provenance, tickets, intents and audit; `015-agent-sync-proof.sql` for proof/replay/diagnostic rows; `016-agent-release-contract.sql` for immutable capability/runtime with safe historical defaults; `017-controller-restore-quarantine.sql` for quarantine markers and reconciliation metadata. Add each to the explicit migration loop in `ControllerDatabase.cs` when its owning task lands, and update `ControllerDatabaseMaintenance` schema checks and backup artifact sidecar rules. Do not alter existing release rows to pretend protocol 2.
