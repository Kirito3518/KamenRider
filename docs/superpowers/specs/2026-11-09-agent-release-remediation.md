# Agent release residual remediation specification

Date: 2026-11-09. Status: tracked follow-on design for review and implementation; no machine action is authorized by this document. Baseline: `0e1fa8e1d8b99e113e5438e614882baf586d3034` and `.superpowers/sdd/2026-11-08-agent-release-management/release-residual-design-draft.md`. This specification closes three release-management residuals together. The existing release feature remains unsafe for production update until these acceptance gates pass.

## Outcome and invariants

An Admin can publish a verifiably applicable Agent ZIP, start an explicit update on one machine even when its installed Agent is legacy, and recover a failed started update with another capable release. The Controller keeps that machine under one continuous maintenance hold from reservation through recovery. Only a current-head outcome report followed by a causally later, enrolled, challenge-capable Agent proof of the expected installed version may close the hold. Updating does not approve a machine or satisfy separate rental readiness, post-boot, hardware, or stream qualification.

The target release and original rollback source are immutable historical facts. A received heartbeat version is a hint until proved. A ticket is authority for its bound purpose and current chain/head/generation only; it is not source provenance, proof of machine exclusion, or permission to choose a successor. No expiry, restart, retry, or DB restore may make a started or inherited hold rentable. No ZIP-supplied script or assembly is executed by the elevated updater or validator.

No worktree is needed for this follow-on. The implementation uses the existing checkout. There is no Reboot Restore Rx inspection or operation. A future full host restart, where specified below, is an explicit per-machine operator action and is not authorization to reboot now.

## Baseline and trust boundary

`AgentAuthentication.Verify` currently checks ±60-second signed time and stores nonce replay only in memory. `SyncEndpoint` loses the verified envelope before `ControllerDatabase.Sync`; `SyncState` writes every received version and readiness. `ReserveAgentUpdate` uses version and `last_seen` from `machine_heartbeats` as a source decision. `AgentSyncCycle` echoes `AgentUpdateChallenge`, but its current client treats every HTTP 200 as a full sync. `LeaseCommandDispatcher.AcceptObservedResponseAsync` clears pending results and calls `ConfirmAsync(response.ActiveLease)`. A challenge-only 200 would falsely acknowledge results and could end an active lease. Existing echo-capable binaries therefore remain **legacy for the new sync protocol** until upgraded.

`AgentReleaseStore` counts physical ZIP entries while `Update-AgentPackage.ps1` counts extracted nodes; their deps and path checks also differ. `public/agent/Update-Agent.ps1` currently runs `Update-AgentPackage.ps1` from the ZIP, which then dot-sources ZIP-supplied `PrivateInstallFiles.ps1` while elevated. A hash-pinned package is not a trusted updater engine: an Admin-uploaded ZIP can carry executable script bytes. Recovery currently renews the same target and uses operation-ID-based local paths. Lease/list/restore code infers the hold from operation statuses rather than an explicit chain.

Trust the authenticated Admin, deployed web and Controller, and an elevated local maintenance helper with protected identity and installation paths. Captured or reordered signed requests, malicious ZIPs, concurrent Admins/updaters, unprivileged local file substitution, crashes, clock movement, and stale DB snapshots are in scope. The shipped Agent `SyncClient` uses ordinary `HttpClient` platform TLS certificate/hostname validation, not a root-thumbprint pin; the PowerShell updater has its separate configured trust-root check. Do not claim Agent response pinning without a future safe bootstrap/rotation design. Compromised Administrator/SYSTEM or stolen exportable enrollment private key is outside attestation; a matching fingerprint proves key possession, not physical host identity or DLL behavior.

## 1. Authenticated freshness and source provenance

### 1.1 Atomic sync acceptance

Split signature verification from timestamp/replay/order acceptance. `SyncEndpoint` passes a sealed server-created `VerifiedAgentRequest` containing machine ID, enrolled public-key fingerprint, method/path, signed seconds, nonce digest, body digest and authenticated body to `ControllerDatabase.Sync`. Malformed, missing or out-of-range signed seconds/signature are 401. A parseable signature-valid but wall-clock-stale protocol-2 sync may receive a rate-limited 428 challenge; a legacy sync outside ±60 seconds is rejected without a success body. Legacy requests inside that window still require durable nonce and strictly increasing signed-second acceptance; equal/lower signed second fails without body effects. The database transaction rechecks the key against current enrollment. Token/replay consumption, proved or diagnostic heartbeat changes, boot/config/command/pairing effects, and update confirmation commit atomically. A rejected request has **no request-body effects**; a 428 may atomically issue or reconstruct its one outstanding token and update bounded issuance bookkeeping. Every production sync/reconcile entry point uses the verified boundary; test-only fixtures explicitly construct verified requests.

Store `last_received_at` and `legacy_reported_version` only as diagnostics. Store `last_proven_version`, `last_proven_sequence`, `last_proven_runtime_epoch` and monotonic proof age separately. A proved unversioned heartbeat clears proved version; an older or unproved request cannot clear or resurrect it. Do not use `last_seen`/diagnostic version as source, version confirmation, or rental readiness. Preserve existing independent readiness and boot gates.

### 1.2 Explicit sync proof protocol 2

Add optional `SyncProofProtocol=2` to the signed `SyncRequest` body and a `SyncChallengeRequired` response on HTTP 428. Only the newly updated `SyncClient` emits this marker and parses 428. On 428, it saves the opaque challenge and returns a no-ack result to `AgentSyncCycle`; the cycle must **not** call `LeaseCommandDispatcher`, apply configuration, observe Controller time as an accepted lease, or clear pending results. It immediately retries with the signed echo. A normal HTTP 200 means the Controller committed the complete request and carries ordinary commands/config/current lease confirmation. Current deployed echo-only clients never receive challenge-only 200 and are not deemed protocol-2-capable merely because they echo the old field.

The Controller maintains per enrolled key mode `legacyUnproven` or `challengeRequired`, a server-issued sequence, current token digest/binding, and last proved sequence. A token is 256-bit HMAC output over a canonical binding including machine/key fingerprint, Controller runtime epoch, unique sequence, purpose `sync`, chain/head/generation and outcome report generation. Keep the HMAC key only in the running Controller. Persist sequence and digest so an unconsumed token can be reconstructed after a lost response in the **same** runtime; never store the bearer token itself. Issuance and consumption serialize in the machine transaction. Concurrent issuers return the same current token. A successful echo consumes it, commits request effects once, and creates the next token. An old/consumed echo gets 428 with the current token and no request effects. Invalid signatures never rotate tokens. At startup rotate runtime epoch and HMAC key, invalidate outstanding tokens and proof ages, and require another round trip; do not reset proved sequence or mode. Bound token lifetime and proof age with a process-monotonic clock; UTC is audit/display, never freshness after a clock rollback. An unavailable/inconsistent monotonic clock fails closed.

The proof request still requires an enrolled signature over exact method/path/body. For a valid protocol-2 echo, signed seconds are audit data rather than a second wall-clock freshness gate. A signature-valid request with parseable but stale signed seconds or stale token may receive bounded 428, but its body has no effects. The new client parses 428 **before** `EnsureSuccessStatusCode`; the old client does not parse it. TLS certificate validation remains required. Token validity does not prove physical machine, and an already signed token-bearing request may be delayed until a later accepted sequence; final update source always comes from local backup evidence.

Any chain/head/generation or outcome-report generation change invalidates old sync tokens. Confirmation requires a token issued after the **current** outcome report, the current head and correct version. Add `reportRequestId` and canonical body digest; exact retry returns the same report result without generation change. Different accepted outcome advances generation and invalidates proofs. Wrong ticket/head/generation, pre-report proof, or legacy echo cannot complete or roll back the operation.

### 1.3 Legacy rollout and availability

An unchanged Agent cannot prove that a captured signed request was created after an Admin action. Signed seconds, nonce order, receipt order, and a wait period cannot repair this. Its version and readiness remain unproved. Keep a durable highest accepted signed second per key for diagnostic legacy receipts; require strictly greater seconds and persist it across Controller restart. Equal/lower, including same-second bursts, do not refresh diagnostic age. Newer unversioned diagnostic receipts clear diagnostic version. Do not silently reset on clock rollback. For signed non-sync endpoints, persist nonce digests with key/path scope and a durable pruning cutoff; a clock rollback must not reopen pruned traffic. Use a separate challenge-bound helper path for first upgrade.

Rollout is fail-closed and per machine. Before enabling the new proof gate, prevent **new** leases for legacy-unproved machines. Drain existing held allocations to their original local deadlines; do not extend them using legacy receipts. A legacy request may only receive a normal 200 if its full ordinary effects are actually accepted and the response accurately reflects any existing active lease; no synthetic empty success is permitted. If safe full-response semantics cannot be established for an active legacy lease, return a non-2xx response so the old client does not clear results or call `ConfirmAsync(null)`; retain the allocation and local deadline enforcement. After drain, the local signed preflight can install protocol-2 Agent while maintenance is held. This may temporarily remove the machine from availability; it does not create rental authority from an unproved replay. Qualification must exercise the deployed old binary and active lease behavior before rollout.

### 1.4 One-time local source binding

Admin reservation checks enrollment, no held allocation/open chain, selected artifact contract and Admin actor in one transaction. It creates a provisional chain/operation and preparation credential without deriving `previous_version` or same-version/downgrade policy from heartbeat. The old receipt remains labeled `legacyReportedPreviousVersion`. A trusted elevated command downloads a deployment-hash-pinned updater engine and maintenance helper over pinned HTTPS into a private protected path. A build-time deployment publisher emits self-contained single-file x64/arm64 helper binaries under content-addressed `public/agent/maintenance/sha256/<hash>/` paths and a deployment-local `agent-maintenance-assets.json` containing schema/helper protocol, fixed URLs, lengths and SHA-256 for both helpers and the web-served PowerShell wrapper. The trusted Next route verifies the local manifest and every on-disk asset, then embeds the selected helper and wrapper hashes in its per-machine command. The bootstrap verifies each fetched script/helper length/hash **before execution**, stages under the owned private tree and rechecks before launch; a user-supplied URL or hash is never accepted. Manifest and command are trusted deployment output under the existing web/Controller boundary, not a publisher-key infrastructure. If the manifest/asset is missing or mismatched, command issuance fails. The ZIP is data only; its scripts are installed as future payload files and never invoked during update. The helper is a small self-contained Windows .NET binary matching **native OS** architecture and sharing verifier/crypto code; do not depend on PS5.1 supporting modern ECDSA import. Bootstrap determines native architecture and canonical Program Files/CommonApplicationData paths through native APIs, independent of 32/64-bit PowerShell process bitness; both shells use the identical protected lock/fence path. It reads existing identity **read-only**, checks ACL/reparse/single-link/ancestor ownership, imports key in memory, compares its fingerprint to enrollment, signs domain-separated canonical evidence and never emits key material. It must not call `DeviceIdentity.LoadOrCreate` as Admin.

The command takes the same installation-wide exclusive lock as all new updater processes before inspection/start and holds its handle through apply/report. That lock does not exclude the live Agent or Stream Guard. Add a separate protected local maintenance fence that overrides stream grants and is continuously enforced by Agent and Guard while held, including during an in-flight `ApplyLease`, pending initial lease, delayed confirmation and restart. Reconcile both current and pending local lease state with Controller held allocations; absence of `lease.json` is not proof of no lease. Unknown state stays held and blocks service mutation. Verify a closed fence and no held local lease continuously before and through service quiescence; recheck after races. It records a protected fsynced journal and obtains a durable Controller start ACK **before any service stop**. The helper requests a purpose-specific source challenge via the HTTPS Agent listener using the scoped preparation credential and a canonical enrollment-key signature; `POST /agent/machines/{machineId}/agent-updates/{operationId}/source-challenge` issues it and `POST .../source-binding` consumes signed evidence with request ID/digest CAS. Neither endpoint accepts a browser actor or ticket alone as proof. It validates/downloads/extracts the target and compares its immutable target runtime (`win-x64` or `win-arm64`) against the helper's independently verified native host architecture **before service stop**. Controller derives and stores target runtime from `Agent/Agent.exe` PE machine type at publication; builder checks its requested `-Runtime` against that PE result. Wrong/unknown architecture is held failure. Under continuous exclusion it stops services with verification, copies the canonical installed tree to an immutable protected backup, verifies bytes/ACL/config and atomically publishes the backup. Source version requires a unique Agent deps project and actual Agent.dll metadata where present. A generated protocol-1 PE/deps installed-tree fixture exercises the parser before mutation; a real deployed machine snapshot must separately qualify the supported old layout. An unsupported or inconsistent source stays `sourceUnverifiable` and held. Dirty versions may have a separate source-only grammar. The resulting snapshot proves backup bytes, not which DLL a previous process had loaded.

After long staging, obtain a fresh one-use `source` challenge bound to key/machine/chain/head/generation/target hash/helper build/runtime epoch. Sign it with native boot ID, source version, backup ID/owner operation ID, canonical tree inventory digest, installed-tree digest and journal phase. The Controller consumes the challenge and binds source/backup **once** in an immutable row; exact retry is idempotent, different bytes conflict. Reject source=target for an ordinary update. Fsync `sourceBound` and check exact Controller ACK/current head before swap. Missing identity, backup, config, safe ACL, challenge, or service state remains held; no heartbeat fallback. First capable target installation never requires legacy sync echo. A rollback to legacy may remain held until a later capable recovery.

## 2. Shared ZIP publication and extraction contract

Create one small .NET package verifier used by Controller publication, retained-artifact reservation/recovery validation, and the trusted maintenance helper. Its bounded archive and extracted-tree inventory has canonical paths, node kinds, lengths, file hashes, total bytes and digest. A separate `AgentPackageVerifier` .NET CLI host is built with the library before the package builder changes; `validate-archive --archive <path> --version <version> --output-json <path>` returns typed category/target runtime and never executes archive contents. PowerShell builder invokes this trusted build output, not the later maintenance helper. PowerShell updater invokes the deployed maintenance helper and retains machine ACL/service/owned-path checks; it does not independently parse manifest/deps or count nodes. Builder validates its completed ZIP before output publication. Existing retained release rows remain immutable; a corrupt artifact becomes unavailable with reason. Validation never loads an uploaded assembly or runs a ZIP script. Test a real builder package through publish/download/extract/stage/fake service apply/rollback. The test corpus uses a generated protocol-2 fixture project with real x64/arm64 PE apphosts and DLL metadata, while production `Agent.csproj` stays at protocol 1 until the client and Controller protocol pass; historical protocol-1 fixtures stay separate.

Format 1 remains exactly six manifest fields; this remediation raises the update-confirmation capability value from 1 to **2** in new builder output. Historical protocol-1 artifacts remain immutable history but are ineligible as a new target or successor and cannot clear a held chain as if they implemented the no-ack challenge response. First upgrade from a protocol-1 installed Agent uses the local signed source preflight and a protocol-2 target, independent of legacy heartbeat proof. A default-closed release-update/supersession gate prevents intermediate implementation from issuing live commands; opening it requires complete implementation, schema, trusted asset manifest, restore admission health and explicit operator qualification. A protocol-2 `SyncProofProtocol` client built during development while its assembly metadata is still 1 is **not** a publishable or eligible release. The builder may assert capability 2 only after the Controller 428 path and new Agent behavior pass together. A later package-format change is required for any new layout or field. Normative acceptance for new publishable/eligible releases:

* Compressed ZIP length 1..104857600 bytes, expanded regular-file bytes at most 524288000. Physical entries at most 5000 **and** materialized non-root nodes at most 5000. Materialized nodes are normalized files plus explicit directories plus the union of all implicit ancestors; shared ancestors count once, extraction root never counts. Duplicate explicit entries reject. Bounded actual reads must equal declared length per entry, during validation and extraction. Compute CRC-32 over actual uncompressed bytes and compare to central-directory CRC even if .NET `ZipArchive` returns data without raising; compute SHA-256 for extracted-inventory matching. Parse and verify local header, central directory and any data descriptor agree on method, name, CRC and sizes and have non-overlapping spans. Reject ZIP64, split/multidisk archives, encryption, unsupported compression, unknown or contradictory extra fields, trailing/overlapping archive data, directory data, corruption/truncation and overflow. Builder output must conform to this structural profile (modify builder if necessary); do not rely on `ZipArchive` CRC behavior.
* Relative `/` paths only; one terminal slash for directories. Reject leading slash/backslash, empty/dot/dotdot segment, NUL/control, colon/ADS, `< > " | ? *`, trailing dot/space, reserved `CON/PRN/AUX/NUL/COM1..9/LPT1..9` including extensions, non-printable or non-ASCII paths, case-insensitive duplicate, file/parent collision and contradictory ZIP attributes. Normalized relative path <=240 characters, segment <=100, depth <=16. The fixed extraction root must meet a tested absolute Windows API path bound. Directory type must agree with terminal slash. Extract into a fresh owned private tree using CreateNew regular files and no ZIP ACL/attribute restoration; reject links/special files. Extracted inventory must match every expected file **and directory**, length and hash, with no reparse/multi-link/extra node.
* Only `Agent` and descendants, the eight root scripts, and manifest are allowed. Required **files** are `Agent/Agent.exe`, `Agent/Agent.dll`, `Agent/Agent.deps.json`, `AgentPackage.manifest.json`, `Install-AgentPackage.ps1`, `Install-Service.ps1`, `Install-TightVncServer.ps1`, `Prepare-SunshineStreamGate.ps1`, `PrivateInstallFiles.ps1`, `ServiceInstallTransaction.ps1`, `Update-AgentPackage.ps1`, `Update-Agent.ps1`. Root scripts/manifest cannot be directories. Forbid `Agent/appsettings.json` case-insensitively and `tightvnc*.msi` at any depth. Local identity/config/data stay separate.
* Manifest is strict UTF-8 JSON object of 1..65536 bytes, depth <=8, exactly case-sensitive keys `packageFormatVersion`, `agentInformationalVersion`, `sourceCommit`, `sourceDirty`, `releaseBuild`, `agentUpdateChallengeProtocol`; case-insensitive duplicate names reject and types never coerce. Values: integer 1, requested version string, lowercase 12-hex commit, boolean false, boolean true, integer **2**. Version length <=64, ASCII grammar `(?:[0-9]+\.[0-9]+\.[0-9]+|1\.0\.0\+g[0-9a-f]{12,40})`, ordinal exact comparison.
* Deps is strict UTF-8 object of 1..16777216 bytes, depth <=32, duplicate names (including casing aliases) rejected throughout relevant objects. `libraries` is an object with **exactly one** key whose project-name portion is Agent case-insensitively, regardless of value/type. Its full key is exactly `Agent/<requestedVersion>` and object has exact string `type=project`. Another Agent key, non-project Agent, wrong version/case, or malformed type rejects in either JSON order. Other projects are allowed.
* `Agent.dll` is read as PE metadata without loading it. Exactly one `AssemblyInformationalVersion` matching requested version and one `AssemblyMetadata("AgentUpdateChallengeProtocol","2")` are required. `Agent/Agent.exe` PE machine type must identify exactly `win-x64` or `win-arm64`; store that target runtime immutably with the release and bind it to ticket/command/evidence. Missing/malformed/duplicate metadata or unknown PE machine rejects. Deps alone and fixture attributes alone do not prove behavior; integration with real builder output, actual wrapper architecture and protocol-2 runtime is required.

One shared adversarial corpus is consumed by Controller publish and retained validation, ticketed download, helper archive validation and helper extracted validation under PowerShell 5.1 and 7. Acceptance **and reason category** agree. Cover physical/materialized bounds (including 5000 entries with >5000 implicit nodes), all byte/path/depth bounds and bound+1, shared/unique/explicit ancestors, collision order, declared/actual mismatch, CRC-only tamper that `ZipArchive` reads without error, local/central/descriptor mismatch, ZIP64/split/overlap/extra/trailing data, forbidden/missing files, deps permutations/duplicates, manifest type/case/extra fields, DLL disagreement/duplicate metadata, x64/arm64/wrong-architecture wrappers, extracted missing/extra file or directory, mutation/reparse/hardlink/partial extraction, and a malicious ZIP script sentinel that must never execute. Validation precedes service mutation. Equivalence means package acceptance, not machine readiness.

## 3. Held maintenance chain and audited supersession

### 3.1 Persistent authority

Add a per-machine maintenance chain with chain ID, current head operation, fencing generation, held/closed state and one-open-chain constraint. Migrate every nonterminal existing operation, including started failed/legacy, into held chains before new software serves requests. Started chain never expires automatically. Operation identity retains machine/chain/parent, immutable target release/version/hash, source binding, original rollback backup owner+digest and historic status. `superseded` is terminal history while the chain stays held; only a transaction that creates its successor may set it. Source/backup/audit rows are append-only or guarded by constraints/triggers. Lease reserve, list rentability, update reserve, ticket predicates, UI and restore validators all use the chain, not `MAX(created_at)` or status sets. Approval and held allocation remain independent.

Every Admin recovery action carries a server-derived Admin actor, reason, request ID, expected head/generation and audit event recording old/new bindings, artifact/evidence digests and transition. Never trust browser actor headers or log tickets/keys. Next.js POST remains same-origin/Admin guarded through `machineApi`; Controller verifies internal listener/credential plus actor role. The bearer ticket cannot select a target.

### 3.2 Two-phase recovery

UI exposes **Retry original target** and **Recover with another release** for a held machine, showing old head/target and retained rollback source. A new target must be a published capable artifact. First Admin creates a recovery intent with expected chain/head/generation and idempotency key. In one CAS transaction the chain remains held, generation advances, all old start/download/status/proof credentials are revoked, and an audit event plus scoped preparation credential are issued. Exact retry returns the same intent; competing or stale request gets 409/current head. Late old proof cannot unlock after intent. Intent expiry never clears inherited hold or revives old tickets.

The elevated new command acquires the installation lock and verifies enrolled identity, challenge, protected journal and old backup. Keep the handle continuously through handoff and successor apply. Busy lock means another new updater is still active; never kill it or infer death from elapsed time. Normalize interrupted state against the **original verified backup** under verified service stop/start, never adopt a failing target as the sole rollback merely because installed. A fully applied incompatible old target may be replaced while retaining the original backup reference and recording actual current installation separately. If evidence/backup is ambiguous, stay held.

The helper submits a one-use signed `recoveryInspection`. One Controller CAS transaction verifies exact intent/head/generation, no held allocation, evidence and selected artifact; appends supersession, creates successor with immutable target/source/original backup references, marks old head superseded, moves head, rotates credentials and appends audit. The transaction exposes no clear-hold gap. Lost response retrieves the **same** successor by intent/request ID. Transaction rollback leaves old held chain and no successor. New ticket binds machine/chain/head/generation/release/hash/purpose with one start and download; all ticket operations require current head/generation, even if an old ticket is unexpired and unused. The same locked process fsyncs successor journal and applies. Revocation cannot recall bytes already downloaded or stop a mutating process; continuous local exclusion is mandatory.

If B fails, original verified A remains rollback authority for recovery to capable C within the same held chain. Preserve B history and A owner/digest. Recovery to A is an explicit restore, not an equal-version reinstall, and needs a fresh capable-source heartbeat to finish; if A is legacy, use distinct capable C or remain held. No automatic endless B retry or SQL unlock.

### 3.3 Legacy local state and process exclusion

Import existing operation IDs, target and paths unchanged. The old updater did **not** write the new-format journal. Under local exclusion (and qualified full restart when old exclusion is unknown), inspect `.Agent-rollback-<oldId>` and stage/prior/restore/install under protected ACL and content inventory, resolve only unambiguous transitions, bind a verified local digest as `legacyImportedLocalInspection`, then create a new journal beginning at an explicit `legacyImported` phase. Never invent earlier phases. `rollback-verified.txt`, old `previous_version`, and a directory name are crash hints, not proof of original running bytes. Do not rewrite old backup or claim historical running-version attestation. The successor refers to old owning operation ID and immutable backup digest. A missing/corrupt **expected new-format** journal or unprovable old backup stays held; it is not treated as an import opportunity.

An updater built before the shared lock can mutate despite ticket revocation. No challenge, new lock, process snapshot or waiting period fences it. If its lock/journal protocol is absent or unknown, supported recovery requires an operator-scheduled **full host restart** while the Controller hold and intent persist, followed by a new locked command. Signed pre-restart evidence captures native boot ID; post-restart evidence requires a different verified native boot ID. Review and prevent known old auto-resume mechanisms through explicit recovery tooling/runbook. Sleep, hibernate, Fast Startup and service restart do not suffice. If exclusion cannot be proved, remain held. A new lock-honoring updater with trustworthy protocol/journal evidence does not require reboot just because the target is legacy. Host snapshot rollback is outside the no-host-rollback assumption and must reenter held recovery. Do not inspect or operate Reboot Restore Rx.

### 3.4 Journal, retries and restore

Use a versioned protected journal per chain with immutable operation entries and fsynced atomic-replace phase/head. Bind enrollment/Controller origin/chain/head/generation/helper protocol/target hash/source inventory/backup owner+digest; store no long-lived ticket/key. Protect journal and backups from Agent-service writes. Check exact owned parent/ancestors, regular single-link files and no reparse before move/delete; never silently repair untrusted ACL/identity. Minimum phases: `inspected`, `controllerStarted`, `targetValidated`, `servicesQuiesced`, `backupPublished`, `sourceBound`, `swapIntent`, `sourceMoved`, `targetPlaced`, `servicesStarted`, `outcomeReported`, `controllerConfirmed`. Write intent before each destructive move, then reconcile actual hashed trees after crash. SQLite and filesystem are not distributed atomic; unexplained mismatch stays held with forensic files preserved.

Start response loss queries request ID/generation before stopping. Backup/source bind retry uses request ID+digest; different bytes conflict. Report retry uses report ID; it never reapplies just to report. Crash during swap reconciles exact trees and can restore referenced verified backup only for known transitions. After confirmation query exact terminal result before later owned-path cleanup. Never delete a backup due to UI timeout. An unstarted **new** chain may expire only before any started/inherited work; recovery chain and unstarted successor cannot expire the inherited hold.

Controller backup/restore includes chains/events/source/backup bindings/credential generations/replay cutoffs and artifact sidecar; machine backup/journal remains local and is reconciled by digest. A restored DB may predate an entire chain or allocation, so restore quarantines **all** rental and update success, including machines absent from the snapshot. Write and durably advance a protected `databasePath + ".restore-epoch"` sidecar outside the SQLite image, under the Controller maintenance lock, using owner/ACL/no-reparse checks and atomic replace/fsync **before** starting external listeners; invalid/unwritable sidecar blocks admission. Runtime proofs, prepared commands and tickets from either epoch are invalid. This sidecar detects restore/deployment generation but does not provide independent machine/allocation/payment/revocation history. The production history provider is currently undefined and must default to unavailable, so restored deployments remain globally quarantined. A future provider must authenticate a durable, complete machine/allocation/payment/revocation event history through the new epoch, including machines absent from the snapshot; only then may per-machine release reconcile local journal/backup digests. A DB field rolled back with the DB cannot provide this. Missing local backup never drops a hold.

## Acceptance and release gate

Deterministic DB/TestServer interleavings, temporary file trees, fake Windows service/fence interfaces and fault injection cover: A/B delivered B/A, same-second versions, unversioned proof clearing, response loss/replay/restart/clock jumps, wrong key/nonce/purpose/head, source backup mismatch, report retry and late proof, lease-vs-reserve and completion-vs-intent races, B-to-C with A rollback, two updaters, live Agent/Guard delayed `ApplyLease` and confirmation while maintenance fence is closing, current and pending local lease reconciliation, legacy full reboot evidence, every journal/DB/rename/stop/start/report boundary, partial restore, and the shared ZIP corpus. Run real builder package through Admin publish/download/extraction/staging and fake apply/rollback; assert malicious ZIP scripts never execute. Test old deployed binary behavior against migration responses and active held lease; no challenge-only 200.

Before any real-machine rollout, independently review the security/state machine, prove the pinned updater/helper build and existing installed Agent source layout, qualify Windows ACL/path/hardlink/native boot behavior and PowerShell 5.1/7, and exercise live service stop/start and stream fence in an authorized machine window. A legacy non-locking updater requires a separately scheduled full restart. The exact old-binary active-lease transition and safe rollout order are **security/availability blockers until tested**; do not infer success from unit fixtures. The external epoch store and independently complete allocation/payment/revocation history source are unresolved deployment prerequisites; restored Controller admission remains globally quarantined until those sources are implemented and reconciled. Test snapshots from before reservation and before supersession. No software can reconstruct a lost backup or attest an old non-locking process death remotely; such machines stay held. Overall rental readiness remains a separate outstanding effort.
