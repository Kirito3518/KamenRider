## Verified installed fork contract

The local executable reports product version `v2026.823.92127` and SHA-256 `3B108A0DD4A3BB5A5231825A500A6C20B5421D65F6AA7FF4BAB88CEBAEF0F20A`. The matching [Foundation Sunshine release](https://github.com/AlkaidLab/foundation-sunshine/releases) points to source commit [`adecdec`](https://github.com/AlkaidLab/foundation-sunshine/tree/adecdec). The checks below are source inspection only; no local management request was made.

- Pairing management registers `POST /api/pin`, but no `GET /api/pin` or `DELETE /api/pin`. The POST body is `{ "pin": "1234", "name": "..." }`; no `pairing_id` is accepted. The route applies the PIN to Sunshine's one current pending client and returns whether Sunshine accepted/sent the server certificate. See the [route and input validation](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/confighttp.cpp#L1657-L1723) and [registered routes](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/confighttp.cpp#L3468-L3519).
- Sunshine permits a single pending PIN request, held internally for up to five minutes. Its management API does not expose that request's identity or a cancellation route. A successful PIN response is not completion proof: the client certificate is added only after the later pairing-secret handshake succeeds. See [pending request handling](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/nvhttp/pairing.cpp#L298-L345), [PIN application](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/nvhttp/pairing.cpp#L600-L700), and [certificate insertion after handshake](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/nvhttp/pairing.cpp#L600-L646).
- `GET /api/clients/list` returns `named_certs` with the saved client name and UUID, so it can confirm a completed handshake. `POST /api/clients/unpair-all` clears saved client certificates and terminates the launched process; it does not cancel a pending PIN request or prove live stream termination. See [client-list response](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/confighttp.cpp#L1954-L1981), [unpair-all handler](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/confighttp.cpp#L1858-L1873), and [certificate removal](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/nvhttp/pairing.cpp#L769-L777).
- GameStream `/cancel` requires a paired-client certificate and asynchronously terminates active sessions. The Agent does not hold a Moonlight client certificate, so it cannot use this endpoint as an administrative stream-stop API. See the [authenticated cancel handler](https://github.com/AlkaidLab/foundation-sunshine/blob/adecdec/src/nvhttp.cpp#L830-L887).

`SunshineClient` now models the installed Foundation contract: it probes `GET /api/clients/list`, exposes a single application pairing-slot token (not a Sunshine client ID), submits `{pin,name}` to `POST /api/pin`, and waits for that unique client name to appear in `named_certs` before reporting success. It uses Basic authentication over HTTPS localhost/loopback, disables redirects and proxies, and keeps normal TLS chain, hostname and expiry validation. `ClearAsync` uses unpair-all, close-app and a verified empty client list; the caller still must prove that the fence terminated existing sessions and pending handshakes because Sunshine has no pending-PIN cancellation API. This assumes a dedicated Sunshine instance per rented machine: unpair-all deletes every saved client, including any administrator clients. The injectable HTTP handler is for deterministic tests only.

## Implemented software boundary

- Owner-only internal endpoints: `GET /internal/leases/{id}/pair/pending`, `POST /internal/leases/{id}/pair`, and `GET /internal/leases/{id}/pair/{commandId}`. POST additionally requires `pairingId` with the brief's `userId`, `pin`, and `idempotencyKey`. Authenticated actor headers come only from the trusted server, behind existing loopback/service-credential middleware. Administrator role alone cannot pair for another tenant.
- Signed agent sync can carry a pending offer bound to rental, revision, boot and expiry. The controller caps offers at 30 seconds and the lease deadline, rejects unoffered IDs, and permits one pending pairing command per rental. Owner retries return the existing command. A different PIN with the same idempotency key also returns that command; it does not replace or retry the PIN.
- PINs never enter SQLite command payloads, idempotency fingerprints, logs, or result errors. They exist in process memory only and are injected into the outgoing command at delivery. Each queued PIN has a one-shot expiry timer that removes its reference while idle and marks its command expired. Completion and boot invalidation purge it during processing; database disposal cancels timers and clears all retained PINs. If the timer cannot update SQLite, the secret is still removed first and a later operation reconciles command status. A controller restart expires undelivered pair commands, requiring a new owner request. Managed strings and HTTP buffers are not guaranteed to be zeroed in memory; process crash dumps must be access restricted.
- Agent selection is bound to its current confirmed scope and a 30-second monotonic offer lifetime. It rechecks after gate waits, rejects stale/duplicate selections, validates command boot/revision/expiry against the enforcer's controller-time floor, and caches command outcomes without retaining the PIN. Cleanup cancels an in-flight submission, serializes behind its completion, and rejects late success before clearing remote state. Changing scope during a handshake, a transport exception, cancellation after submission, or a malformed submission response requires successful fenced cleanup before another offer.
- `SunshineClient` restricts its configured management origin to HTTPS localhost/loopback with no path, credentials, query or fragment. The production transport disables redirects and proxies, uses Basic authentication, and retains normal TLS chain, hostname and expiration validation. No certificate bypass callback exists. Provision a certificate trusted by Windows and matching the configured localhost/IP name before any integration; certificate provisioning and ACL-protected credential loading are not implemented here. The injectable transport is for deterministic tests.

## Deliberately unavailable production pieces

`SunshineClient.CheckReadyAsync` returns false. An authenticated management endpoint alone cannot prove an interactive desktop, usable capture encoder, audio/input device, or stream isolation. `UnverifiedStreamGate` returns false rather than pretending it blocked traffic. Neither Sunshine client nor pairing session is registered in the production host; its optional dispatcher path therefore reports pairing unavailable, sends no offers, and `SyncWorker` continues reporting unknown readiness. The default `ClosedStreamGate` now throws when asked to block because it cannot prove Sunshine ingress or active sessions were fenced; this fails boot/lease operations closed and does not close an independently running Sunshine server.

The [official Windows firewall installer](https://github.com/LizardByte/Sunshine/blob/master/src_assets/windows/misc/firewall/add-firewall-rule.bat) creates program-wide inbound TCP and UDP allow rules. Adding a narrow allow rule cannot establish default deny while broader allows still apply. No script to change the user's firewall is included.

## Required qualification before enabling the adapter

1. Record installed version, executable hash, service account and matching versioned API source. For this Foundation build, implement and verify one-pending PIN submission, handshake completion via client-list, and the absence of a pending-cancel API on a dedicated test host.
2. Provision local management TLS trust and service-only credential ACLs. Verify wrong certificate name, untrusted certificate, expiration, redirect, wrong credentials and unavailable management API all prevent readiness.
3. Design and install a closed-from-boot network/service fence, accounting for every pre-existing Sunshine allow, every profile/interface, IPv4/IPv6, custom base-port offsets and router/NAT mappings. Ensure the management loopback remains available. Prove isolation before Sunshine accepts network clients and throughout agent startup/reconciliation, service restart, agent crash and offline expiry. A future `AllowAsync` must require the controller-confirmed lease and actual desktop readiness; no allow implementation exists yet.
4. With real Moonlight clients, prove rejection before activation; successful owner-authorized PIN submission; rejection of concurrent/expired pairing attempts; active stream termination and old-client reconnect rejection after expiry; cancellation during every pairing-handshake stage; and no certificate resurrection after cleanup. Firewalling new connections alone does not prove termination of existing sessions. Since this fork has no pending-PIN cancellation route and its unpair-all operation does not stop Sunshine itself, qualify a service stop/restart or other fence fallback before enabling pairing.
5. Wire the qualified fence, credential loader, desktop health probe and lease lifecycle cleanup into host registration. Only then enable PrepareMachine/readiness and streaming permission. Task 7 must invoke fenced cleanup before releasing/reassigning a machine. Automated fake transport/gate tests are not substitutes for these checks.
