# Agent operations and Restore Rx qualification

## Deployment status

This repository is **not operationally ready for rentals**. There is no qualified default-closed stream gate, restoration evidence, or desktop health provider. The Agent remains fail-closed pending those providers; cross-boot import and offline crash-time deadline durability are not fully qualified. Live service installation is disabled for both roles. Do not enable services or expose Sunshine based on a green unit test, a successful HTTP call, or service recovery.

## Installation preparation

Run `scripts/agent/Test-HostReadiness.ps1` in PowerShell 7 for a read-only inventory of local service, Sunshine firewall, elevation and certificate prerequisites. It does not change Restore Rx, firewall rules, services or credentials. A certificate count is not TLS qualification, and the report deliberately keeps `StreamFenceQualified` and `ReadyForRental` false until a real fence and live rental test exist.

Publish without installing: `./scripts/agent/Publish-Services.ps1 -Role Both -OutputDirectory C:\KamenRaiderPublish -Plan`. Remove `-Plan` to publish self-contained Windows binaries into separate Controller/Agent directories. This does not start them.

Use a protected executable directory (normally under Program Files); standard users and tenants must have no write access. Provision role-specific config using absolute data paths, then inspect `Install-Service.ps1 -Plan` with Role, PublishDirectory, DataDirectory, ConfigurationFile and TrustedRootThumbprint. **Live installation is disabled** until the directory trust and reparse-point race, service-creation rollback, and operational qualification are resolved. The plan describes intended service accounts and recovery settings; it does not install or configure services.

The guarded installation code attempts to remove a newly created service if later configuration fails. This is not a filesystem transaction: a data directory's ACL or the published configuration may already have changed, and service removal can itself fail. An administrator must inspect the service, data directory, and configuration before any retry; do not assume files or permissions were restored. Parent and leaf checks and mock rollback tests are preliminary, not evidence that all executable dependencies or race conditions are protected.

Provision certificate trust through the organization's approved process. Verify the expected root fingerprint out of band and install the root in LocalMachine Root; the installer only checks its presence, never imports an untrusted certificate. Provision Controller HTTPS server certificate/private-key ACL for its account, verify hostname/SAN and chain, and verify Agent validation against that chain. Do not bypass validation. Controller internal HTTP listener stays loopback on a different port. Provision its service credential through an ACL-protected config or approved secret store; never put real credentials into Git or command arguments. Sunshine management credentials and trusted localhost certificate still need the Task 6 service-only loader; this installer does not supply one. No firewall changes are performed.

Example Agent configuration (no secrets):

```json
{"ControllerUrl":"https://controller.example.invalid:7443","DataDirectory":"C:\\ProgramData\\KamenRaider\\Agent","MoonlightPort":47989,"SunshinePort":47990,"NetworkAdapterId":"REPLACE_WITH_QUALIFIED_ADAPTER_ID"}
```

Controller config needs InternalUrl (`http://127.0.0.1:7442`), AgentUrl (`https://controller.example.invalid:7443`), absolute DatabasePath and a separately provisioned ServiceCredential. Populate certificate binding per deployment. Never copy Controller config to Agent or embed tenant credentials/pairings in either image.

## Per-machine baseline

1. Qualify the installed Restore Rx edition/version using its vendor-supported workflow. Restore-on-every-boot behavior is a deployment requirement; no Restore Rx API or command is implemented here.
2. Register the device, set ports/name/price and approve it. Save a per-machine baseline containing that device's own private identity and service configuration. Never clone an identity to another machine.
3. The baseline must contain no tenant game accounts, tenant files, Moonlight paired clients or pending pairing requests. Protect any persistent exclusion containing device identity/config from tenant writes. Decide whether local lease state survives rollback; the authoritative lease stays on Controller either way.
4. Enable restore for every Windows boot and perform a cold boot. Prove tenant files/game accounts/pairing disappear, identity remains the same, and the latest Controller config replaces the older baseline revision before any ready report.
5. Repeat with active streams, old client reconnect, process-only service restart, network outage, hibernate/fast startup and expiry during downtime. A service restart uses the same native Windows boot identifier. A changed identifier proves an OS boot occurred; it does **not** prove restoration happened.

`baselineValidated` is an operator installation attestation. It is never per-boot proof that Restore Rx actually restored a volume. A qualified restoration evidence provider must independently supply that proof for the current boot; until it exists, reconciliation holds. Same-boot restart still requires qualified proof and fresh fenced cleanup/health checks; it cannot manufacture restoration from a new process ID.

## Reconciliation contract and limits

Signed `POST /agent/reconcile` uses the same registered-device signature, timestamp and nonce boundary as `/agent/sync`. The first request carries bootId, appliedConfigRevision and baselineValidated. Controller issues a random persisted one-time challenge bound to the requested boot, exact held allocation ID and lease revision, current lease state/pending proposal, command generation and configuration revision. The challenge expires after 30 seconds and survives Controller restart. The proof request echoes that challenge with explicit restorationVerified/fencedCleanupVerified/healthVerified evidence (all default false). The trusted Agent must collect fresh evidence in a serialized startup flow; Controller cannot independently observe disk restoration or Windows stream state. Do not set these flags from operator configuration or transport success.

The first call fetches current configuration and challenge with evidence false. Agent persists config, then gathers all evidence for that exact challenge before submitting proof. A missing, consumed, superseded, expired, wrong-boot or changed-allocation/revision/state challenge returns Hold. Validation and consumption occur atomically with the transition; a delayed prior proof cannot act on a replacement rental. Agent persists config before submitting evidence. Controller requires approval and exact current config revision. Missing proof returns Hold without releasing allocation. Full proof retires older boots/commands, invalidates pending commands including pairing, clears offers and uncommitted extensions. Only a still-active, unexpired committed lease can return ResumeLease, with its original absolute expiry and committed revision. Preparing leases become failed. Expired/ending/failed leases never resume; fenced reconciliation releases their held allocation and returns PrepareAvailable without sending a shutdown command. Reconciliation records notReady; action and readiness do not grant stream permission or tenant approval.

Call reconciliation **before** starting ordinary sync on a new boot. Existing sync intentionally turns a boot-mismatched active lease into ending. Such a lease is not revived by reconciliation. This conservative fallback may end a valid rental if ordering is wrong. Production wiring must serialize startup, reconcile/import the durable lease with a monotonic deadline using total request elapsed time, and only then start command sync. It must retain the real default-closed gate throughout. Same-boot known expiry enforcement must continue independently of network, cleanup and persistence. Do not add a new lease duration on resume, replay delayed old-boot commands or revive an expired lease.

Production completion additionally requires tested fenced lifecycle cleanup and fresh proof binding to the current lease/boot, a live gate closed before Sunshine/network startup and on service failure, health/capture/input/audio checks, cross-boot lease import, and real machine qualification. `docs/sunshine-compatibility.md` lists the remaining Sunshine tests. These are deployment blockers, not completed tests.

## Installation review blocker (2026-10-30)

The reviewed installer hardening requires an empty data destination (including hidden entries), rejects reparse-point destinations, and checks emptiness again after replacing the directory ACL. `PrivateInstallFiles.ps1` provides these file-only helpers. Configuration is staged in a restricted empty directory, given an explicit protected ACL before secret bytes are written, flushed, then atomically renamed on the same volume with that ACL. Allowed principals are the service account, SYSTEM, Administrators and the installing owner (installation requires an elevated administrator). Existing broad target ACLs are not retained. The helpers have been exercised only on disposable temporary files, including failure before publication.

Windows antivirus previously blocked access to the updated `scripts/agent/Install-Service.ps1`; the user subsequently allowed access and the script was read and tested in plan mode. Security review found unresolved directory-parent trust and reparse-point races, plus incomplete rollback after service creation. The live installation path is therefore explicitly disabled; do not use an earlier revision to work around this guard. File-only helper tests and plan checks do not qualify a live installation.
## Controller backup and recovery

Controller SQLite contains machine identities, approvals, allocations, commands and configuration. Use SQLite's online backup API (or `sqlite3` `.backup`) against the live database to produce a consistent snapshot; do not copy only the database file while WAL writes are active. Alternatively stop the Controller cleanly before copying the database and associated state. Encrypt backups, restrict access and retain them according to the operator's policy. Test recovery in an isolated environment with network access and service startup disabled; validate database integrity and that the backup contains the expected machines and leases. Neither a backup nor a restore drill has been performed here.

Back up Controller TLS private keys/certificates, trust roots and service credentials separately in an approved protected secret store, with recovery permissions and certificate expiry tracked. Agent private identities are per-machine; protect each separately and never clone one to another machine. If an identity is lost or compromised, isolate the machine and revoke its existing identity through the approved operator process, then provision a new key, re-enroll and explicitly approve it after verifying its fingerprint. This repository does not yet provide a complete operator revocation/re-enrollment recovery workflow; do not claim that this procedure has been validated. Reconcile held allocations conservatively and do not restore service until the missing gate and proof integrations are qualified.

Web authentication data and its secrets have their own backup and restore process and consistency requirements; a Controller SQLite backup does not back up web authentication. Coordinate recovery points and review sessions and credentials after restoring either store. Avoid bringing an old snapshot online as production without assessing stale leases, identities and revoked credentials.
