# Agent operations and Restore Rx qualification

## Deployment status

This repository is **not operationally ready for rentals**. There is no qualified default-closed stream gate, restoration evidence, or desktop health provider. The Agent remains fail-closed pending those providers; cross-boot import and offline crash-time deadline durability are not fully qualified. The Agent installer has a live service-install path; `AGENT_INSTALL_ENABLED=false` only withholds the generated command from the admin web page and is not an installer-side safety lock. Do not enable Sunshine or claim rental readiness based on a green unit test, a successful HTTP call, or service recovery.

The guarded installation code attempts to remove a newly created service if later configuration fails. An administrator must inspect the service, data directory, and configuration before any retry; do not assume files or permissions were restored. Parent and leaf checks and rollback tests are preliminary, not evidence that all executable dependencies or race conditions are protected. No live service installation has been performed on this development host.

Controller internal HTTP listener stays loopback on a different port. Provision its service credential through an ACL-protected config or approved secret store; never put real credentials into Git or command arguments. ## Per-machine baseline

1. Qualify the installed Restore Rx edition/version using its vendor-supported workflow. Restore-on-every-boot behavior is a deployment requirement; no Restore Rx API or command is implemented here.
2. Register the device, set ports/name/price and approve it. Save a per-machine baseline containing that device's own private identity and service configuration. Never clone an identity to another machine.
3. The baseline must contain no tenant game accounts, tenant files, Moonlight paired clients or pending pairing requests. Protect any persistent exclusion containing device identity/config from tenant writes. Decide whether local lease state survives rollback; the authoritative lease stays on Controller either way.
4. Enable restore for every Windows boot and perform a cold boot. Prove tenant files/game accounts/pairing disappear, identity remains the same, and the latest Controller config replaces the older baseline revision before any ready report.
5. Repeat with active streams, old client reconnect, process-only service restart, network outage, hibernate/fast startup and expiry during downtime. A service restart uses the same native Windows boot identifier. A changed identifier proves an OS boot occurred; it does **not** prove restoration happened.

`baselineValidated` is an operator installation attestation. It is never per-boot proof that Restore Rx actually restored a volume. A qualified restoration evidence provider must independently supply that proof for the current boot; until it exists, reconciliation holds. Same-boot restart still requires qualified proof and fresh fenced cleanup/health checks; it cannot manufacture restoration from a new process ID.

## Reconciliation contract and limits

Signed `POST /agent/reconcile` uses the same registered-device signature, timestamp and nonce boundary as `/agent/sync`. The first request carries bootId, appliedConfigRevision and baselineValidated. Controller issues a random persisted one-time challenge bound to the requested boot, exact held allocation ID and lease revision, current lease state/pending proposal, command generation and configuration revision. The challenge expires after 30 seconds and survives Controller restart. The proof request echoes that challenge with explicit restorationVerified/fencedCleanupVerified/healthVerified evidence (all default false). The trusted Agent must collect fresh evidence in a serialized startup flow; Controller cannot independently observe disk restoration or Windows stream state. Do not set these flags from operator configuration or transport success.

The first call fetches current configuration and challenge with evidence false. Agent persists config, then gathers all evidence for that exact challenge before submitting proof. A missing, consumed, superseded, expired, wrong-boot or changed-allocation/revision/state challenge returns Hold. Validation and consumption occur atomically with the transition; a delayed prior proof cannot act on a replacement rental. Agent persists config before submitting evidence. Controller requires approval and exact current config revision. Missing proof returns Hold without releasing allocation. Full proof retires older boots/commands, invalidates pending commands including pairing, clears offers and uncommitted extensions. Only a still-active, unexpired committed lease can return ResumeLease, with its original absolute expiry and committed revision. Preparing leases become failed. Expired/ending/failed leases never resume; fenced reconciliation releases their held allocation and returns PrepareAvailable without sending a shutdown command. Reconciliation records notReady; action and readiness do not grant stream permission or tenant approval.

Call reconciliation **before** starting ordinary sync on a new boot. Existing sync intentionally turns a boot-mismatched active lease into ending. Such a lease is not revived by reconciliation. This conservative fallback may end a valid rental if ordering is wrong. `SyncWorker` now passes a production lease importer to `BootReconciler`; after proof and Controller confirmation, it imports the same lease into `LeaseEnforcer` with a monotonic deadline derived from controller time and total request elapsed time. If Controller confirms `PrepareAvailable` after proof, the importer durably clears an old-boot snapshot; it refuses to clear a lease from the current boot so an Agent service restart cannot skip expiry shutdown. Do not start command sync before reconciliation. The default environment still rejects restoration, cleanup and health proof, and the current `ClosedStreamGate` throws for both allow and block because no qualified adapter exists. `LeaseEnforcer` only opens a gate after the exact active lease is confirmed; failed opens keep streaming unconfirmed and set a retryable fault. Same-boot known expiry enforcement must continue independently of network, cleanup and persistence. Do not add a new lease duration on resume, replay delayed old-boot commands or revive an expired lease.

Production completion additionally requires tested fenced lifecycle cleanup and fresh proof binding to the current lease/boot, a live gate closed before Sunshine/network startup and on service failure, health/capture/input/audio checks, a hardware-verified cross-boot lease import, and real machine qualification. `docs/sunshine-compatibility.md` lists the remaining Sunshine tests. These are deployment blockers, not completed tests.

## Controller backup and recovery

Controller SQLite contains machine identities, approvals, allocations, commands and configuration. The published Controller executable now has an online, verified backup command:

```powershell
.\Controller.exe --backup-database 'C:\ProgramData\KamenRaider\Controller\controller.db' 'D:\KamenRaiderBackups\controller-YYYYMMDDTHHMMSSZ.db'
```

`BackupDatabase` creates a consistent snapshot while the Controller is running and blocks database writes while the snapshot is copied. The command validates SQLite integrity, foreign keys and required Controller tables before atomically publishing the backup. Choose a destination directory with restricted ACLs, encrypt the backup at rest and retain it according to the operator's policy. [Microsoft's SQLite backup documentation](https://learn.microsoft.com/dotnet/standard/data/sqlite/backup) describes the online backup behavior.

Restore only in an isolated recovery drill or a planned maintenance window. Stop the Controller first, then run:

```powershell
.\Controller.exe --restore-database 'D:\KamenRaiderBackups\controller-YYYYMMDDTHHMMSSZ.db' 'C:\ProgramData\KamenRaider\Controller\controller.db' --controller-stopped
```

The restore command requires the explicit `--controller-stopped` acknowledgment and refuses while a current Controller process holds the database activity lock. It validates a staged copy before replacing the destination atomically and preserves the previous database beside it as a `.pre-restore-*.db` recovery file (with raw `-wal`/`-shm` sidecars if the prior database is corrupt). Verify the reported result, start the Controller only in the isolated environment, and confirm expected machines, leases and configuration. Do not perform a restore on the development Controller currently running on this workstation.

Back up Controller TLS private keys/certificates, trust roots and service credentials separately in an approved protected secret store, with recovery permissions and certificate expiry tracked. Agent private identities are per-machine; protect each separately and never clone one to another machine. If an identity is lost or compromised, isolate the machine and revoke its existing identity through the approved operator process, then provision a new key, re-enroll and explicitly approve it after verifying its fingerprint. This repository does not yet provide a complete operator revocation/re-enrollment recovery workflow; do not claim that this procedure has been validated. Reconcile held allocations conservatively and do not restore service until the missing gate and proof integrations are qualified.

Web authentication data and its secrets have their own backup and restore process and consistency requirements; a Controller SQLite backup does not back up web authentication. Coordinate recovery points and review sessions and credentials after restoring either store. Avoid bringing an old snapshot online as production without assessing stale leases, identities and revoked credentials. The code path is covered with temporary databases; no production backup or restore drill has been performed.

## Stream Guard installation transaction (2026-11-06)

The Agent package includes `Prepare-SunshineStreamGate.ps1`. Its `-Plan` (or `-Action Plan`) reports the automatic LocalSystem `KamenRaider Stream Guard`, the virtual-account `KamenRaider Agent` dependency, manual-start `SunshineService` with its existing dependencies preserved, and the enabled inbound all-profile/all-protocol program block `KamenRaider Stream Guard - Sunshine`. Plan does not query or mutate live services/firewall rules. `-InstallScriptRoot` supports the package's in-memory invocation.

A fresh package installation verifies the effective firewall profiles and local-policy permission, publishes/verifies the exact closed rule, stops Sunshine, creates the Guard with recovery actions, and changes only Sunshine startup/dependencies before Agent enrollment starts. Existing broad vendor allow rules are preserved. Conflicting managed rules, existing Agent/Guard services and incomplete installations are rejected; a complete installation's enrollment repair must validate the installed Guard, Agent dependency, Sunshine configuration and closed firewall policy first.

Setup rollback uses an in-memory ownership record: it restores Sunshine startup/dependencies, removes only its own Guard/new rule, restores a reused rule's enable state, and resumes previously running Sunshine only after successful restoration. If rollback cannot restore the fence/configuration, it reports the failure and retains the Guard, closed policy and protected binaries for administrator recovery. It is not a crash-durable installer journal or a transaction for all filesystem ACL/config changes.
