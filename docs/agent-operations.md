## Per-machine baseline

1. Qualify the installed Restore Rx edition/version using its vendor-supported workflow. Restore-on-every-boot behavior is a deployment requirement; no Restore Rx API or command is implemented here.
2. Register the device, set ports/name/price and approve it. Save a per-machine baseline containing that device's own private identity and service configuration. Never clone an identity to another machine.
3. The baseline must contain no tenant game accounts, tenant files, Moonlight paired clients or pending pairing requests. Protect any persistent exclusion containing device identity/config from tenant writes. Decide whether local lease state survives rollback; the authoritative lease stays on Controller either way.
4. Enable restore for every Windows boot and perform a cold boot. Prove tenant files/game accounts/pairing disappear, identity remains the same, and the latest Controller config replaces the older baseline revision before any ready report.
5. Repeat with active streams, old client reconnect, process-only service restart, network outage, hibernate/fast startup and expiry during downtime. A service restart uses the same native Windows boot identifier. A changed identifier proves an OS boot occurred; it does **not** prove restoration happened.

`baselineValidated` is an operator installation attestation. It is never per-boot proof that Restore Rx actually restored a volume. A qualified restoration evidence provider must independently supply that proof for the current boot; until it exists, reconciliation holds. Same-boot restart still requires qualified proof and fresh fenced cleanup/health checks; it cannot manufacture restoration from a new process ID.

## Reconciliation contract and limits

Signed `POST /agent/reconcile` uses the same registered-device signature, timestamp and nonce boundary as `/agent/sync`. The first request carries bootId, appliedConfigRevision and baselineValidated. Controller issues a random persisted one-time challenge bound to the requested boot, exact held allocation ID and lease revision, current lease state/pending proposal, command generation and configuration revision. The challenge expires after 30 seconds and survives Controller restart. The proof request echoes that challenge with explicit restorationVerified/fencedCleanupVerified/healthVerified evidence (all default false). The trusted Agent must collect fresh evidence in a serialized startup flow; Controller cannot independently observe disk restoration or Windows stream state. Do not set these flags from operator configuration or transport success.

The first call fetches current configuration and challenge with evidence false. Agent persists config, then gathers all evidence for that exact challenge before submitting proof. A missing, consumed, superseded, expired, wrong-boot or changed-allocation/revision/state challenge returns Hold. Validation and consumption occur atomically with the transition; a delayed prior proof cannot act on a replacement rental. Agent persists config before submitting evidence. Controller requires approval and exact current config revision. Missing proof returns Hold without releasing allocation. Full proof retires older boots/commands, invalidates pending commands including pairing, clears offers and uncommitted extensions. Only a still-active, unexpired committed lease can return ResumeLease, with its original absolute expiry and committed revision. Preparing leases become failed. Expired/ending/failed leases never resume; fenced reconciliation releases their held allocation and returns PrepareAvailable without sending a shutdown command. Reconciliation records notReady; action and readiness do not grant stream permission or tenant approval.

Call reconciliation **before** starting ordinary sync on a new boot. Existing sync intentionally turns a boot-mismatched active lease into ending. Such a lease is not revived by reconciliation. This conservative fallback may end a valid rental if ordering is wrong. `SyncWorker` now passes a production lease importer to `BootReconciler`; after proof and Controller confirmation, it imports the same lease into `LeaseEnforcer` with a monotonic deadline derived from controller time and total request elapsed time. If Controller confirms `PrepareAvailable` after proof, the importer durably clears an old-boot snapshot; it refuses to clear a lease from the current boot so an Agent service restart cannot skip expiry shutdown. Do not start command sync before reconciliation. `StreamGuardBootEnvironment` delegates boot pairing cleanup through `ISunshinePairingSession.ClearAsync`; it reports `passed` only when that session completes its Guard-backed cleanup, `blocked` when cleanup returns false, and `unavailable` when the provider throws. `BootReconciler` reaches cleanup only after baseline and restoration pass; those default evidence providers remain unavailable, so current reconciliation stops before cleanup. Desktop health and runtime health evidence also remain unavailable. `AgentHost` uses `StreamGuardPipeClient`; a missing or unresponsive Guard fails closed, and the host has not been qualified on a real rental machine. `LeaseEnforcer` only opens a gate after the exact active lease is confirmed; failed opens keep streaming unconfirmed and set a retryable fault. Same-boot known expiry enforcement must continue independently of network, cleanup and persistence. Do not add a new lease duration on resume, replay delayed old-boot commands or revive an expired lease.

Production completion additionally requires tested fenced lifecycle cleanup and fresh proof binding to the current lease/boot, a live gate closed before Sunshine/network startup and on service failure, health/capture/input/audio checks, a hardware-verified cross-boot lease import, and real machine qualification. `docs/sunshine-compatibility.md` lists the remaining Sunshine tests. These are deployment blockers, not completed tests.

## Controller backup and recovery

Controller SQLite contains machine identities, approvals, allocations, commands and configuration. The published Controller executable now has an online, verified backup command:

```powershell
.\Controller.exe --backup-database 'C:\ProgramData\KamenRaider\Controller\controller.db' 'D:\KamenRaiderBackups\controller-YYYYMMDDTHHMMSSZ.db'
```

`BackupDatabase` creates a consistent snapshot while the Controller is running and blocks database writes while the snapshot is copied. The command validates SQLite integrity, foreign keys, required tables and columns, declared column types, required nullability and primary keys, plus the exact allocation and command-revision uniqueness rules, before publishing the backup. The command also reads the release rows from that exact snapshot, verifies every referenced ZIP by content-addressed path, size and SHA-256, and copies them into a sibling `<backup-file>.agent-releases/sha256/<prefix>/<sha256>.zip` tree. The artifact tree is published first and the database file last; treat the database file as the completion marker and retain both together. Missing/corrupt artifacts or an existing destination cause failure without publishing a new database backup. Validation failures report status without printing database row contents. Choose a destination directory with restricted ACLs before running the command; artifact files inherit that protected directory. Preserve its ACLs when copying the database and sidecar tree off-host, encrypt the backup at rest and retain it according to the operator's policy. [Microsoft's SQLite backup documentation](https://learn.microsoft.com/dotnet/standard/data/sqlite/backup) describes the online backup behavior.

Restore only in an isolated recovery drill or a planned maintenance window. Stop the Controller first, then run:

```powershell
.\Controller.exe --restore-database 'D:\KamenRaiderBackups\controller-YYYYMMDDTHHMMSSZ.db' 'C:\ProgramData\KamenRaider\Controller\controller.db' --controller-stopped
```

The restore command requires the explicit `--controller-stopped` acknowledgment and refuses while a current Controller process holds the database activity lock. It validates the staged database and the complete referenced artifact set before replacing the destination. Missing/corrupt sidecar artifacts, conflicting existing destination bytes, directory collisions or reparse-point artifact paths fail closed before any release file is installed or database is replaced. An existing valid content-addressed ZIP is reused; it is never overwritten. Restore copies missing ZIPs with no-overwrite publication, rebases only the private artifact paths in the staged database to the new host, reinstates the immutable-row trigger, revalidates the staged database, and publishes it last. Unreferenced destination artifacts and other protected data are retained. It preserves the previous database beside it as a `.pre-restore-*.db` recovery file (with raw `-wal`/`-shm` sidecars if the prior database is corrupt). A valid pre-restore snapshot has its own verified `.agent-releases` sidecar so it can also be restored on a clean host; missing/corrupt artifacts referenced by that prior valid database abort replacement. A corrupt prior database is retained as raw forensic recovery material, not claimed as a verified restorable snapshot. A failed later copy removes only artifact files created by that restore attempt; previous artifacts remain untouched. Verify the reported result, start the Controller only in the isolated environment, and confirm expected machines, leases and configuration. Do not perform a restore on the development Controller currently running on this workstation.

**Current startup restriction:** the independent machine/allocation/payment/revocation history provider is unavailable. Therefore every startup of an existing Controller database durably enters global rental and update quarantine, even when the protected restore epoch matches the database. A matching epoch cannot detect an offline snapshot copied back during the same Controller run. Only a verified first install at a database path with no database or restore artifacts starts outside quarantine. The explicit epoch bootstrap provisions the marker but never clears quarantine. Do not reopen rentals after restart or restore until an independently authenticated complete history source is implemented and reviewed.

Keep the backup database and its `.agent-releases` directory under the same protected backup location. Verify a clean-host restore using a disposable destination before relying on a recovery point; the command verifies hashes itself and never searches arbitrary old absolute paths. A legacy database-only backup with no release rows can still be restored. A legacy backup with release rows requires the operator to reconstruct the exact `<backup-file>.agent-releases/sha256/...` sidecar from a trusted retained artifact backup; filenames, lengths and SHA-256 must match the rows. Without those bytes, restore refuses rather than inventing or downloading replacement releases. Do not edit immutable release rows or overwrite an existing conflicting ZIP to bypass that failure. A crash can leave a sidecar tree without the final database completion marker; keep it for diagnosis and choose a new backup filename for a retry. New directories may remain after a failed restore; they contain no accepted replacement database. Existing allocations/tickets come from the selected database recovery point, so reconcile newer independent allocation/payment history before reopening rentals.

Back up Controller TLS private keys/certificates, trust roots and service credentials separately in an approved protected secret store, with recovery permissions and certificate expiry tracked. Agent private identities are per-machine; protect each separately and never clone one to another machine. If an identity is lost or compromised, isolate the machine and revoke its existing identity through the approved operator process, then provision a new key, re-enroll and explicitly approve it after verifying its fingerprint. This repository does not yet provide a complete operator revocation/re-enrollment recovery workflow; do not claim that this procedure has been validated. Reconcile held allocations conservatively and do not restore service until the missing gate and proof integrations are qualified.

Web authentication data and its secrets have their own backup and restore process and consistency requirements; a Controller SQLite backup does not back up web authentication. Coordinate recovery points and review sessions and credentials after restoring either store. Avoid bringing an old snapshot online as production without assessing stale leases, identities and revoked credentials. The code path is covered with temporary databases; no production backup or restore drill has been performed.

## Agent update recovery qualification (2026-11-17)

Recovery supersession is deliberately fail-closed and requires three deployment/operator inputs before the Controller will create a successor operation for a held update chain:

- `AgentMaintenancePinnedHelperSha256` — the exact 64-hex SHA-256 of the deployed maintenance helper build. Empty (the default) keeps every recovery inspection blocked as `helperBuildNotPinned`. The pin must come from the verified deployment manifest, never from the request or the Agent.
- `AgentMaintenanceExclusionProcedureQualified` — set true only after the operator has actually completed the documented qualification (old updater proven not running, or a full host restart with a changed native boot ID). False (the default) blocks as `exclusionProvenanceUnavailable`.
- `AgentMaintenanceQualifiedOldUpdaterAutoResumeStatus` — `qualifiedNotApplicable` (continuous shared lock) or `qualifiedDisabled` (verified full host restart). It must match the signed inspection.

Qualified inspections additionally require the previous operation's immutable backup owner/digest, a protocol-2 release artifact that still validates, no held lease allocation, and a changed/same native boot ID consistent with the declared exclusion provenance. On success the Controller creates the successor operation and fresh recovery ticket, moves the held chain head/generation, marks the previous head `superseded`, closes the intent, and records an immutable successor evidence row (migration 021) plus a `recoveryInspectionQualified` audit entry in one transaction.

`POST /internal/machines/{id}/agent-updates/{operationId}/recovery-ticket` remains intentionally fail-closed (409 Conflict): it never reissues or extends a ticket. Recovery authority is only the audited successor ticket returned by the inspection commit; an unstarted update whose ticket expired must be reserved again, and a failed update must go through the recovery-intent inspection path.
